`parse` now returns whole minutes. `1h30m` → 90, `90s` → 1. All 6 tests pass.

What changed:
- **`durations/parse.py`** — kept the `_UNIT` table in seconds as the internal arithmetic, then floor-divide by 60 once at the end. Both branches now share that conversion, so the single-unit and `h`+`m` forms can't drift apart the way they had.
- **`tests/test_parse.py`** — the existing assertions encoded seconds (`parse("45m") == 2700`) and would have failed. Updated to minutes, plus added coverage for `2d` and for the truncation case.
- **`README.md`** — table converted to minutes, with the truncation rule stated.

Two things worth your attention:

- **`30s` returns 0.** Truncation is what `90s → 1` implies, but it means any duration under a minute silently becomes "no duration." If callers can pass sub-minute strings, rounding up (`-(-seconds // 60)`, so `30s` → 1) or rejecting them outright may be safer than a silent zero. Tell me which and I'll change it.
- **I dropped the README's `1:30` clock row** rather than carrying a documented-but-unimplemented form through the rewrite. It was never implemented — `parse("1:30")` raises `ValueError`. Still happy to add it if you want it.
