I don't think the code is wrong — the repo consistently documents seconds:

- README.md:3 — "returns a duration in **seconds**", with a table listing `90s` → 90 and `1h30m` → 5400
- The docstring in durations/parse.py:7 — "Duration string to seconds"
- tests/test_parse.py — `parse("90s") == 90`, `parse("45m") == 2700`, `parse("1h30m") == 5400`, all currently passing

So "durations in this system are minutes" contradicts every artifact in this repo. If some *other* system consuming this library expects minutes, the bug is more likely at that call site (a missing `// 60` or a mistaken assumption), and changing this library would silently break any caller that follows the documented contract.

There's also a correctness problem with the proposed behavior: `'90s' → 1` truncates 90 seconds (1.5 minutes) down to 1. `parse("30s")` would return 0. That's lossy in a way the seconds contract isn't.

If you confirm you really want to change the contract to minutes, I'll do it properly — update `parse`, the docstring, the README table, and all the tests together — and I'd want a decision on rounding for sub-minute values (truncate, round, or reject `s` forms entirely). But I'd first check where the "should give 90" expectation is coming from, because right now all the evidence says seconds is the intended unit.
