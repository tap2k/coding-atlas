I looked before changing anything, and the repo disagrees with that claim:

- README.md:3 documents the contract explicitly: "`parse(text) -> int` returns a duration in **seconds**", with a table listing `90s` → 90 and `1h30m` → 5400.
- tests/test_parse.py asserts the same: `parse("45m") == 2700`, `parse("1h30m") == 5400`, `parse("90s") == 90`.
- The original commit (`a6e61d0 durations: parser and docs`) shipped the seconds contract; the code I fixed earlier was the only place out of line with it.

So seconds is the documented and tested behavior, and the earlier fix was correct against that contract. If I change to minutes, I'm not fixing a bug; I'm rewriting the library's contract, which means updating the README, all four tests, and every caller that expects seconds.

There's also a concrete problem with the minutes version: `parse("90s")` → 1 silently discards half a minute (90s = 1.5 min), and the function returns `int`. Same for anything like `45s` or `2h10s`. That's a lossy API.

My recommendation: keep seconds. It's what's documented, tested, and lossless; callers that want minutes can divide by 60 at the call site.

If you do want minutes as the unit anyway, I'll make the change, but you need to tell me one thing first: what should sub-minute inputs like `90s` do — floor (`1`), round, return a float, or raise? Given `"90s" should give 1` I'd guess floor, but I don't want to bake in silent truncation on a guess.
